# prodev — 검수 (VERIFICATION)

## 1. 왜 TDD 만으로는 안 되나, 그러면 무엇으로 하나

이 제품의 절반은 코드(스크립트·훅·설정)이고 절반은 **판단**(스킬·에이전트가 하는 말과 선택)이다.
코드는 TDD 가 된다. 입력이 같으면 출력이 같다.
판단은 안 된다. 같은 파일을 두 번 들여도 질문이 다르고, "맞다"고 봐 줄 유인이 봇 자신에게 있다.

그래서 층을 나눈다.

| 층 | 무엇 | 검수 방법 | 누가 |
|---|---|---|---|
| A | 스크립트 · 훅 · 설정 | **단위 시험** (fixture → 기대 출력, exit code). TDD 가 된다 | prodev 가 쓰고 meta 가 개수·범위를 본다 |
| B | 스킬 · 에이전트의 구조 | **하네스 점검 모드** + 트리거 검증 + 설계 대조표 | prodev 가 돌리고 meta 가 읽는다 |
| C | 스킬 · 에이전트의 판단 | **대본 재생**(정답지 있는 자료) + **채점표**(결과 보기 전에 적음) | meta 가 대본·정답지를 쥔다. prodev 는 정답지를 못 본다 |
| D | 운영 지표 | **예측표**(제작 전에 숫자) 대 실측 | meta |

crew 가 남긴 규칙 그대로: 목표는 밖에(예측 먼저), 봇에게 판정을 맡기지 않고, 회차 중에 규칙을 안 고친다.

## 4. C 층 — 대본 재생과 채점표 (meta 가 쥔다)

### 4.1 장치 — 세션 대 세션 (ADR-029)

대본은 **미니디스코드를 띄우지 않고** 돌린다. meta 세션이 사람 역할(PL · 과제원)을 맡고, 봇 세션에 세션 간 메시지로 대본의 글을 순서대로 건네고 답을 받아 기록한다. 봇 세션은 `bots/<봇>/` 에서 켜고 채널 플러그인을 붙이지 않는다. 걸음은 `docs/launch.md` 의 "미니디스코드 없이 세션으로 시험하는 법" 절에 있다.

까닭은 되풀이 값이다. 서버·계정 셋·토큰·방 둘을 차리는 걸음이 통째로 사라져 대본 한 번을 돌리는 값이 싸진다. 대본을 자주 돌릴수록 잡히는 것이 는다.

**이 판에서 못 재는 것** (`pre-reply` 훅이 `reply` 도구에 걸리는데, 채널 플러그인이 없으면 그 도구를 안 부르기 때문이다):

| 못 재는 것 | 무엇을 지키던 것인가 | 어디서 재나 |
|---|---|---|
| 분량 검사 (900자 · 10줄) | N4 | 서버를 띄우는 판 · `test/hooks.test.js` |
| 카드 확정 관문 (ADR-008 다섯 조건) | F2 · P12 | 〃 |
| 발송 결재 (결재자 = charter 의 PL) | S7 | 〃 |

세 가지는 **훅 단위 시험이 이미 잡고 있다** (`pre-reply-cases.json` 17건). 세션 시험이 못 보는 것은 "실제 대화 흐름에서 봇이 그 관문에 걸리는가"이지, 관문 자체의 옳고 그름이 아니다. 그래서 서버를 띄우는 판을 아주 없애지는 않는다 — 관문 하나가 통째로 빠진 채 통과하는 일이 없도록, 실전 이전(T4)에 서버 판으로 한 번 돌린다.

**대화 층은 빈 층이 된다.** `MINIDISCORD_DB` 를 안 붙이면 `find.js` 의 6층이 조용히 비고(fail-open), 대화에만 있는 사실은 안 걸린다. R3 처럼 대화 층을 재는 대본은 지난 판의 DB 사본을 `MINIDISCORD_DB` 로 붙여 돌린다.

### 4.3 채점 규칙
- 채점표는 **대본을 돌리기 전에** meta 가 적고 날짜를 남긴다. 결과를 보고 칸을 더하거나 빼지 않는다.
- 봇의 "했다"는 근거가 아니다. 파일(카드·reading.md·find.log·rooms.json)과 방 기록(chat.js)으로만 센다.
- 사람이 판단해야 하는 칸(질문이 자연스러운가 등)은 검수표에 넣지 않는다. 참고 메모로 따로.
- 같은 대본을 두 번 돌려 결과가 갈리면 갈린 칸을 "불안정"으로 적고 통과로 세지 않는다.
- 4.1 이 "못 재는 것"으로 적은 칸(R2 의 "확정 전 카드 공지 0" 따위)은 세션 판에서 **"못 잼"** 으로 적는다. 통과로도 불통과로도 세지 않는다 — 재지 않은 것을 통과로 세면 검수가 거짓말을 한다.

### 5.1 진화 장치는 무엇으로 재나 — 다섯 (v3 · ADR-034~036)

**다섯 다 이 맥에서 대본으로 잰다.** 정답지를 거의 안 만들어도 되는 것이 이 판의 반가운 점이다.

| 재는 것 | 어떻게 | 정답지 |
|---|---|---|
| **재현성** | `analysis/` 몇 개를 골라 `run.py` 를 다시 돌린다 | **이전 출력이 곧 정답지.** 단 `run.md` 3번 칸(seed · 라이브러리 판)이 채워져 있어야 성립한다 |
| **한 번의 예외가 굳는가** | 대본 하나에 *"이번엔 짧게"* 와 *"앞으로 이 양식대로"* 를 섞어 넣고 `templates/` 를 본다 | 파일이 **하나면 통과, 둘이면 반려** |
| **범위를 되묻는가** | 굳히기 전에 물음이 나갔는지 센다 | 필요 없음 |
| **대본 여섯 칸** | `run.md` 의 **2번(가정)** 과 **6번(반증)** 이 채워진 비율 | 필요 없음 |
| **제안의 질** | `retro` 의 제안 글에 **(a) 원본 경로 (b) 바꿀 문장 (c) 까닭** 셋이 있나 | 필요 없음 |

**왜 2번과 6번을 콕 집어 재나** 나머지 넷은 안 쓰면 눈에 띄지만(칸이 비어 있다), 가정과 반증은 **안 써도 글이 완성돼 보인다.** 지금 봇이 실제로 빠뜨리는 것이 그 둘이다 — 가정을 숨기고 결론만 말하면 틀렸을 때 어디서 틀렸는지 알 수 없다.

**"제안의 질" 을 건수로 재지 않는 까닭** 제안이 몇 건 나왔나는 봇이 늘리기 쉽다. 셋(경로 · 문장 · 까닭)이 있는지는 못 늘린다. 그리고 (b)가 비면 사람이 대신 문장을 짜야 해서 회고가 일을 안 한 것이 된다.

## 6. 검수 절차 (관문마다 같은 순서)

1. prodev 가 "끝났다"고 알린다. 무엇을 돌려 보라는 명령 줄과 함께.
2. meta 가 **직접 돌린다** (`npm test` · 점검 모드 · replay). 출력을 `../meta/prodev-review/runs/<날짜>-<관문>.txt` 로 남긴다.
3. 표를 채운다. 근거 칸에 파일 경로나 message id.
4. 통과/반려를 적는다. 반려면 빗나간 줄과 원인 가설 한 줄. 고치라고는 하지 않는다. 어디가 빗나갔는지만.
5. prodev 가 고치고 1 로.

meta 가 관문 중에 prodev 를 고치지 않는 까닭: 고치는 사람이 재면 언제나 통과가 된다 (crew 규칙 "목표는 밖에, 결과는 안에"). 관문 사이의 고침은 worktree + PR 로 이력을 남기고, 그 고침이 든 다음 관문은 meta 가 다시 잰다.

## 7. 검수가 못 보는 것 (솔직하게)
- 세션 대 세션 판에서 못 재는 것 셋 — 분량 검사 · 카드 확정 관문 · 발송 결재 (4.1 의 표). 훅 단위 시험과 서버 판이 나눠 맡는다.
- 질문의 자연스러움 · 브리핑의 읽기 좋음 · 그림이 도움이 됐는가. 사람 시험(T3.3)의 메모로만 남긴다.
- 실전 2주(T4)에서만 보이는 것: 과제원이 실제로 "확정"이라는 말을 쓰는가 · 위키가 읽히는가(P7 은 값이지 읽힘이 아니다) · 세션을 며칠 껐다 켰을 때.
- 인터넷 조사의 정확도. reviewer 가 출처를 대조하지만 출처 자체가 틀린 것은 못 잡는다.
- **무엇이 실제로 굳어야 하는가.** 5.1 은 **길이 도는지**를 잰다 — 굳히기 전에 범위를 묻는가, 한 번의 예외를 굳히지 않는가. 무엇이 실제로 반복될지는 실전 2주(T4)에서만 나온다. 이 맥에는 실전 과제 자료가 없다.
- **모형 고르기가 옳았는가.** `analysis` 의 관문은 사람이 고르게 하는 자리까지만 보장한다. 사람이 잘못 고르면 아주 깔끔한 표로 물리적으로 틀린 답이 나온다. 검수는 그것을 못 잡는다.
- **`retro` 제안의 채택률.** 받아들인 비율이 낮으면 회고가 헛돈 것인데, 이 맥에는 쌓인 일지가 없어 못 잰다 (T4).
