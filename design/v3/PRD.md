# prodev — 과제 비서 · 제품 요구사항 (PRD)

작성 2026-09-10. 자리: 이 문서는 prodev 저장소의 것이다. 설계의 뿌리는 `../meta/prodev-review/plans/2026-09-10-pl-assistant.md` 와 그 검토 결과이며, 여기에는 **요구사항만** 옮겼다. 구조는 `ARCHITECTURE.md`, 결정의 까닭은 `ADR.md`, 만드는 순서는 `TASKS.md`, 검수는 `VERIFICATION.md`.

## 1. 한 줄

**공정개발 과제의 PL 과 과제원이 사내망 채팅(minidiscord)에서 비서 봇 하나와 일하면, 과제 발의부터 자료 정리 · 리서치 · 일정 · 특허 · 논문 · 보고까지 한 자리에서 이어지고, 사람은 "모두를 다 아는 봇"과 일한다고 느낀다.**

### 1.1 v3 이 더하는 한 줄 (ADR-031)

**쓸수록 이 사람에게 맞아 가는 비서 — 같은 말을 두 번 하지 않아도 되는 것.**

보고 양식을 한 번 가르치면 다음부터 그 양식으로 나오고, 분석 방법을 한 번 만들면 다음에 또 짜지 않는다. 그래야 prodev 가 이 과제 하나의 비서로 끝나지 않고 **어느 과제에 붙여도 거기서 다시 똑똑해지는 뼈대**가 된다. 성공 지표는 기능 수가 아니라 **잔소리가 줄어드는 것**이다.

나머지 요구는 관문 B 에서 이 절에 채운다 (`TASKS.md` 5단계).

## 2. 왜 만드나

- crew 실험(봇 다섯, 회차 다섯)이 닫혔다. 순차형 연구 과제에서 봇 다섯은 같은 품질에 싱글 세션의 15~19배를 물었고, 사실이 봇 계층을 넘으며 떨어졌다 (`../crew/EVOLUTION.md` S3 부록·정정).
- 그 실험이 남긴 것은 셋이다: 검토는 다른 문맥에서 해야 값을 한다 · 세는 것은 기계가 해야 한다 · 예측을 먼저 적어야 판정이 선다. prodev 는 이 셋 위에 **봇 하나**를 세운다.
- 고영혁(고넥터) 사례 분석(`../meta/prodev-review/notes/external-evidence-gonnector.md`)에서 가져온 것은 셋뿐이다: 상세한 발의 문답 · 그림으로 묻기 · 사람이 정정하는 자리를 정해 두기.
- minidiscord 의 진짜 장점은 봇을 여럿 두는 것이 아니라 **사람을 여럿 들이는 것**이다. PL 혼자 쓰는 Claude Code 가 아니라 과제원 전원이 같은 두뇌를 쓴다.

## 3. 누가 쓰나

| 사람 | 무엇을 하나 | 권한 |
|---|---|---|
| PL (과제 리더) | 발의 · 결재 · 방향 · 보고 | 전부 |
| 과제원 | 실험 자료 올리기 · 문답 · 물음 · 일정 등록 · 리서치 요청 | **PL 과 같게 전부** (사람 결정 2026-09-10). 다만 헌장·논문 와꾸·보고서 발송의 결재는 PL 이 한다 |
| 비서 (봇) | 아래 시나리오 전부 | 스스로 새 일을 만들지 않는다 |

과제원은 사내망 브라우저로 PL PC 의 minidiscord 에 접속한다. 설치할 것이 없다.

## 4. 시나리오 (요구사항의 뼈대, 사람이 적은 순서 그대로)

| # | 시나리오 | 비서가 해야 하는 것 | 남아야 하는 것 | 사람이 정하는 지점 |
|---|---|---|---|---|
| S1 | 과제 발의 | 목적·목표·일정·인원·예산·판정 기준을 **하나씩** 묻고 헌장 초안을 낸다 | `charter.md` · `schedule.md` 뼈대 · 방 둘 | 헌장 결재 (PL) |
| S2 | 실험 자료 들이기 | `files` 방에서 파일을 열어 읽고, "이렇게 읽었습니다" 표를 보이고, 모르는 것을 셋 이하로 묻고, 그림이 나은 자리는 그림으로 묻고, 과제원이 고치면 기다리고, "확정"이 오면 카드로 만들어 그 방에 **카드 한 줄**로 공지한다 | 원본(불변) · 사이드카 · 실험 카드 · 카드 공지 글 · 위키 갱신 | 과제원의 "확정" |
| S3 | 결과 논의 → 리서치 | 기존 자료를 먼저 찾고, 없으면 물음을 문장으로 적어 허락을 구하고, 조사해서 10줄로 브리핑하고, 몇 턴 대화 뒤 카드로 굳힌다 | 리서치 문서 · 리서치 카드 | 시작 허락 · 카드 굳힘 |
| S4 | 일정 | 등록·변경·"지금 할 일" 브리핑. 파일이 진실 | `schedule.md` · 결정 카드 | 없음 |
| S5 | 특허 | 헌장·카드에서 청구 후보 → 선행 조사 → 전략 3갈래 이하 | 선행 조사 · 전략 문서 | 조사 범위 · 청구 방향 |
| S6 | 논문 | 카드·리서치를 모아 와꾸 → 절마다 초안 + 근거 카드 | 와꾸 · 초안 · 그림 | 와꾸 결재 · 절마다 통과 |
| S7 | 주간·월간·경영진 보고 | 기간을 잘라 방향 셋을 묻고, 사람이 준 포맷 파일의 칸을 채운다. 숫자마다 카드 출처 | 보고서 파일 | 방향 선택 · 발송 결재 |
| S0 | 언제나 | 대화 전체를 검색해 답한다. 껐다 켜도, 압축돼도, 파일에서 되살아나 "이어서 합니다" 한 줄로 잇는다 | 일지 · handoff · 열린 실 | 없음 |

## 5. 요구사항

### 5.1 기능 (F)

| # | 요구 | 어떻게 확인하나 |
|---|---|---|
| F1 | 비서는 과제의 방 둘(본방 `prodev-<과제>` · `prodev-<과제>/files`)에 다 있고, **어느 방에서든 답한다**. 과제는 방 이름이 아니라 `PRODEV_PROJECT` 로 안다 (ADR-012 · ADR-022) | 방 둘에 @TO 하면 둘 다 그 방에서 답한다 |
| F2 | 들이기는 S2 의 순서를 따르고, **과제원의 "확정" 글이 없으면 카드 공지가 나가지 않는다** (기계가 막는다. 방아쇠는 방이 아니라 `[카드]` 표식이다, ADR-022) | 확정 없이 카드 공지를 시도하면 훅이 막고 이유를 남긴다. 평소 답에서 카드 번호를 말하는 것은 안 막힌다 |
| F3 | 카드의 알갱이는 **실험 한 건**이다. 파일 여럿이 한 실험이면 카드 하나 | 파일 셋 올린 실험이 카드 하나로 남는다 |
| F4 | 물음에는 정해진 순서(**색인 → 카드 → 위키 → 과제 문서 → inbox 사이드카 → 대화**)로 찾고, 답에 출처(경로 또는 `#message_id`)를 단다. 순서는 층 **이름**으로 적는다 — 번호는 층이 늘 때마다 밀린다 (ADR-016 · ADR-026) | 물음 20개 중 출처 없는 답 0 |
| F5 | 대화는 무제한으로 검색된다. 봇은 서버 커서에 기대지 않고 방 전부에서 놓친 @TO 를 찾는다 | 꺼진 사이 글 5건 → 켜면 5건 다 처리 |
| F6 | 압축 직전에 인수인계서를 만들고 압축 뒤 첫 답에 "이어서 합니다"를 쓴다. 사람이 끊김을 못 느낀다 | 압축 뒤 방을 잘못 짚은 답 0, 하던 실을 이어간다 |
| F7 | 긴 일(3분 초과)은 백그라운드로 넘기고 그 턴은 "시작했습니다"로 끝낸다. 다른 사람의 물음이 막히지 않는다 | 리서치 중 다른 방 물음에 1분 안에 답한다 |
| F8 | 리서치·특허·논문·보고 산출물은 사람 결재 전에 **다른 문맥의 검토**를 한 번 거친다 | 검토 판정 파일이 산출물마다 있다 |
| F9 | 일정은 파일 하나가 진실이고 브리핑은 그 파일과 어긋나지 않는다 | 브리핑 5회, 파일과 어긋남 0 |
| F10 | 원본은 불변이다. 같은 이름이 다시 오면 옆에 `.v2` 로 둔다. 지우지 않고 void 로 바꾼다 | 덮어쓰기 0, 삭제 0 |
| F11 | 색인은 기계가 만든다. 머리말을 못 읽으면 조용히 넘기지 않고 실패한다 | 깨진 머리말 하나 → exit 1 |
| F12 | 봇이 그림(잘라낸 사진 · csv 그래프)을 방에 올려 물을 수 있다 | 들이기 문답에 그림 첨부 1회 이상 |
| F13 | 방을 이유로 답을 거부하거나 다른 방으로 보내지 않는다. 딱 하나의 예외가 본방에 온 파일이다 — 안내 한 줄만 하고 읽기를 시작하지 않는다 | 방을 이유로 미룬 답 0 · 본방 첨부 1건에 안내 한 줄 · 그 건으로 생긴 `inbox/` 폴더 0 |

**v3 이 더하는 다섯 (F14~F18, ADR-034~036).** 앞 열셋이 "과제를 잇는" 요구라면 이 다섯은 **"쓸수록 맞아 가는"** 요구다.

| # | 요구 | 어떻게 확인하나 |
|---|---|---|
| F14 | **사실은 자동으로 는다. 규칙은 사람이 세운다.** 경계는 "되돌릴 수 있는가" — 카드·위키·일지는 틀려도 다음 것이 덮으니 봇이 쌓고, 규칙은 그 뒤 모든 판에 영구히 작용하니 사람이 **"앞으로"** 라고 말했을 때만 굳는다 | 봇이 스스로 `house.md` 에 규칙을 더한 건수 **0** |
| F15 | 굳히기 전에 **범위를 한 줄 되묻는다.** 승인이 아니라 경계다 ("회의록만인가요, PL 께 나가는 문서 전부인가요"). 물음은 하나 | 굳힌 건마다 범위 물음이 앞에 있다 |
| F16 | **"이번에는" 을 "앞으로는" 으로 듣지 않는다.** 한 번의 예외는 굳지 않는다 | 대본 하나에 "이번엔 짧게" 와 "앞으로 이 양식대로" 를 섞어 넣는다 → `templates/` 파일이 **하나면 통과, 둘이면 반려** |
| F17 | 굳은 파일 머리에 **언제부터 · 누가 정했나 · 무엇을 보고 만들었나.** 석 달 뒤 "왜 이렇게 됐지" 에 답할 수 있어야 한다 | 굳은 파일마다 셋이 있다 |
| F18 | 분석 한 건 = `analysis/<날짜>-<slug>/`(`run.py` · 여섯 칸 `run.md`) **+ 카드 하나.** 카드는 선택이 아니다 — `analysis/` 는 찾기 층에 없다. 같은 물음이 다시 오면 새 폴더를 만들지 않고 앞 카드를 댄다 | `run.md` 의 2번(가정) · 6번(반증) 이 찬 비율 · 같은 물음에 생긴 새 폴더 **0** · `run.py` 를 다시 돌려 같은 숫자가 나오나 |

**세는 장치를 만들지 않는다.** 봇이 반복을 알아채는 쪽(관찰형)은 횟수를 들고 있는 상태 파일도 · 점수도 · 등급도 쓰지 않는다. 일지에 한 줄씩 적어 두고 `retro` 가 읽는다 (ADR-035 · 036).

### 5.2 비기능 (N)

| # | 요구 | 값 |
|---|---|---|
| N1 | 들이기 한 건 값 | ≤ $3 (표준단가 환산) |
| N2 | 들이기 한 건 문답 왕복 | 중앙값 ≤ 4 |
| N3 | 찾기 성공률 — **index · 카드 · 위키 · 과제 문서** 층이 답한 비율. 층 **번호로 적지 않는다**: 번호는 층이 하나 늘 때마다 밀려서, 숫자로 적은 지표는 그때마다 조용히 틀린 것을 재게 된다 (ADR-026) | ≥ 70% |
| N4 | 사람에게 보내는 글 | 900자 · 10줄 안 (기계가 센다) |
| N5 | 비서 지침(CLAUDE.md) | 40줄 안. 절차는 스킬, 세는 것은 훅 |
| N6 | 세션은 상주하지 않는다. 주간에 켜고 끈다 | 켤 때 파일에서 되살아난다. 놓친 @TO 0 |
| N7 | 승인 요청 | 하루 ≤ 3 (허용 목록으로) |
| N8 | `house.md` (과제의 규칙) | 50줄 안. 넘으면 훅이 자르고 봇이 사람에게 말한다. **줄이는 것은 사람** (ADR-032) |
| N9 | `retro` 의 제안 | 항목마다 근거(일지 날짜 · `find.log` 줄 · 카드 번호). **근거 없는 항목 0**. 사람이 받아들인 비율이 낮으면 회고가 헛돈 것이다 |

## 6. 범위 밖 (이번에 안 만든다)

- 봇 여럿 · 봇끼리의 대화 · 캐릭터 이름. 떼어 내는 규칙은 `ARCHITECTURE.md` 3절에 두되 첫 판에서는 안 쓴다.
- minidiscord 서버 코드 수정 (웹 검색창 · 스레드). 설정 한 줄(`MINIDISCORD_BOT_FILES_DIR`)만.
- 봇의 "성장" · 일기에서 지혜 승격. 계측이 없는 것은 안 한다.
- 사내망 밖 배치 · 보안 강화.

## 7. 성공의 정의

제작이 끝났다는 말은 `VERIFICATION.md` 의 검수표를 meta 가 채우고, 예측(`../meta/prodev-review/predictions/prodev-prediction.md`)의 열에 맞은 것이 열 중 여덟 이상일 때다. 느낌으로 판정하지 않는다.
